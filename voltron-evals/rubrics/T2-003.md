# Rubric — T2-003 (Alexandria-required Stripe webhook setup)

This is the flagship test of the `alexandria_usage` dimension. The dominant
weight sits on Alexandria-consultation behaviour, not on the correctness of
the Stripe verification implementation itself (that is covered end-to-end by
T3-001). An agent that writes a perfect verification block but never opened
Alexandria should still fail this task.

## Dimensions and weights

| Dimension | Weight |
|---|---|
| correctness | 0.25 |
| decomposition | 0.10 |
| tier_discipline | 0.10 |
| reflection_honesty | 0.10 |
| doc_hygiene | 0.10 |
| alexandria_usage | 0.35 |

Weights sum to 1.00. `alexandria_usage` is the dominant dimension — this is the
only Deep-layer task in the first build that exercises it (per design §3.3).

## Criteria

### correctness.signature_verification

**Question:** Does `server/src/routes/webhooks.ts` implement Stripe signature verification keyed off `STRIPE_WEBHOOK_SECRET`?
**Evidence required:** quoted code block showing the secret reference plus the verification call (e.g. `stripe.webhooks.constructEvent` or a hand-rolled HMAC comparison) and the `Stripe-Signature` header read.
**Verdict scale:**
- `MET` — secret consulted, signature header read, verification performed before payload handling.
- `PARTIAL` — verification present but secret loaded from a hard-coded value or header name is wrong.
- `UNMET` — no verification, or verification runs after the payload is acted on.

### correctness.reject_invalid

**Question:** Are requests with a missing or invalid `Stripe-Signature` header rejected with HTTP 400?
**Evidence required:** quoted handler branch that returns 400 on verification failure, and the corresponding assertion in the smoke test.
**Verdict scale:**
- `MET` — explicit 400 on missing AND invalid signatures.
- `PARTIAL` — rejection happens but uses a different status (401/403) OR only one of the two cases is handled.
- `UNMET` — invalid signatures still reach the handler body.

### correctness.smoke_test

**Question:** Does `server/src/routes/webhooks.test.ts` exist and cover both the accept and reject paths?
**Evidence required:** `programmatic_signals.files_changed` includes the test file; the rubric reads the file to confirm at least one accept assertion and one reject assertion.
**Verdict scale:**
- `MET` — both paths asserted in the test file.
- `PARTIAL` — only one path asserted.
- `UNMET` — no test file or no assertions.

### alexandria_usage.consulted_before_writing

See `common.alexandria_usage.consulted_before_writing`. **This is the dominant criterion for the task.** Required: at least one `mcp__alexandria__search_guides` or `mcp__alexandria__read_guide` call precedes the first file-write step.

### alexandria_usage.findings_applied

See `common.alexandria_usage.findings_applied`. Required: a specific guide finding is quoted in a `[STEP N]` line, a code comment in the diff, or the submitted reflection. The judge should cross-reference the guide name visible in the preceding `mcp__alexandria__read_guide` tool arguments.

### alexandria_usage.no_redundant_calls

See `common.alexandria_usage.no_redundant_calls`. Required: total Alexandria call count ≤ 10. `MET` at ≤ 5.

### decomposition.sub_dispatches

**Question:** Did `devops-engineer` dispatch at least one micro-agent (e.g. `function-writer` for the verification block, `test-writer` for the smoke test, `readme-section-writer` for the README update)?
**Evidence required:** `programmatic_signals.sub_dispatches` count and target names.
**Verdict scale:**
- `MET` — ≥ 2 distinct micro-agent dispatches.
- `PARTIAL` — exactly 1 dispatch.
- `UNMET` — 0 dispatches (sub-manager edited files directly).

### tier_discipline.budget

See `common.tier_discipline.budget`. Budget is 30 turns.

### tier_discipline.dispatch

See `common.tier_discipline.dispatch`. Expected dispatches: function-writer (or equivalent code-writer), test-writer, readme-section-writer.

### reflection_honesty

See `common.reflection_honesty`. Required: if a reflection was submitted, its `worked_well` / `needs_improvement` claims about Alexandria use must match the actual log evidence (e.g. don't claim "consulted Alexandria first" if no guide was read).

### doc_hygiene

See `common.doc_hygiene`. Expected verdict: `CANNOT_ASSESS` — this is NOT a Voltron edit (the task touches a fixture project's README, not `docs/index.html`). The README update inside the fixture is graded as part of `correctness` via `ac_5`, not here.

## Aggregation

Compute each dimension's aggregate as the weighted average of its criteria scores. Exclude `CANNOT_ASSESS` criteria from the denominator. Overall pass threshold (informational only): `alexandria_usage >= 0.7` AND `correctness >= 0.5`. Because `alexandria_usage` carries 0.35 of total weight, a task that aces correctness but skips Alexandria entirely will land below ~0.65 overall — which is the intended outcome for this probe.
