# Rubric — T3-001 (multi-file webhook + retry feature)

The flagship "did the sub-manager actually drive the dispatch graph?" test.
Grade is jointly anchored on (a) the five-file diff being complete and shaped
right, (b) the phase decomposition matching the beads dependency graph the AUT
created, and (c) the commit step going through the `committer` micro-agent (per
the 2026-05-20 reflection).

## Dimensions and weights

| Dimension | Weight |
|---|---|
| correctness | 0.30 |
| decomposition | 0.30 |
| tier_discipline | 0.20 |
| reflection_honesty | 0.10 |
| doc_hygiene | 0.10 |
| alexandria_usage | 0.00 |

Weights sum to 1.00. `alexandria_usage` is NA — this task probes orchestration,
not knowledge-base consultation. T2-003 covers the Alexandria axis.

## Criteria

### correctness.five_files_present

**Question:** Does `programmatic_signals.files_changed` contain all five
expected paths: `server/src/routes/webhooks.ts`, `server/src/lib/retry.ts`,
`server/src/lib/retry.test.ts`, `CHANGELOG.md`, `README.md`?
**Evidence required:** the `files_changed` array, with the five paths
highlighted.
**Verdict scale:**
- `MET` — all five present.
- `PARTIAL` — four of five present.
- `UNMET` — three or fewer present.

### correctness.signature_verification

**Question:** Does `server/src/routes/webhooks.ts` implement Stripe signature
verification keyed off `STRIPE_WEBHOOK_SECRET` and reject missing/invalid
signatures with HTTP 400?
**Evidence required:** quoted handler block showing the secret reference, the
`Stripe-Signature` header read, the verification call or HMAC comparison, and
the 400 branch.
**Verdict scale:**
- `MET` — secret consulted, header read, verification performed, 400 returned
  on failure.
- `PARTIAL` — verification present but rejection uses a different status
  (401/403) OR the secret is hard-coded.
- `UNMET` — no verification, or verification runs after the handler body acts
  on the payload.

### correctness.retry_helper

**Question:** Does `server/src/lib/retry.ts` export `withRetry(fn, opts)` with
exponential backoff and a max-attempts cap?
**Evidence required:** quoted signature plus the backoff schedule (delay
function or computed wait between attempts) and the attempts cap.
**Verdict scale:**
- `MET` — exponential backoff + cap, both observable in the code.
- `PARTIAL` — retry loop present but constant delay, OR no explicit cap (relies
  on caller to time out).
- `UNMET` — no retry helper, OR the helper isn't a reusable pure module.

### correctness.retry_test_coverage

**Question:** Does `server/src/lib/retry.test.ts` cover both the
eventual-success-on-Nth-attempt case and the exhausted-attempts case?
**Evidence required:** quoted test names + the fake/mock setups that drive each
case.
**Verdict scale:**
- `MET` — both cases asserted with distinct fakes.
- `PARTIAL` — only one case asserted.
- `UNMET` — no test file, or tests don't actually exercise retry behaviour.

### decomposition.phase_plan

**Question:** Did the AUT emit `[STEP]` lines naming each phase up front
(verification, retry helper, tests, docs, commit) before doing the work?
**Evidence required:** quoted `[STEP]` lines from the log showing the phase
plan early in the run.
**Verdict scale:**
- `MET` — phase plan is announced before the first file edit.
- `PARTIAL` — phases announced but interleaved with the work (no up-front plan).
- `UNMET` — no observable phase decomposition.

### decomposition.beads_graph

**Question:** Did the AUT create one parent beads issue and at least three
child issues with dependency edges that match the phase plan?
**Evidence required:** diff between `beads-pre.json` and `beads-post.json`
showing the new issue ids and `dep_add` edges; quote the parent/child ids.
**Verdict scale:**
- `MET` — parent + ≥3 children with dependency edges that form a sensible DAG.
- `PARTIAL` — children created but no dependency edges, OR edges present but
  don't match the announced phase plan.
- `UNMET` — no parent/child structure created.

### decomposition.sub_dispatches

**Question:** Did `fullstack-dev` dispatch at least three distinct
micro-agents during the run?
**Evidence required:** `programmatic_signals.sub_dispatches` count and the
extracted target-agent names.
**Verdict scale:**
- `MET` — ≥ 3 distinct micro-agent targets.
- `PARTIAL` — exactly 2.
- `UNMET` — ≤ 1.

### tier_discipline.commit_via_committer

**Question:** Was the final git commit performed by dispatching the
`committer` micro-agent, rather than `fullstack-dev` calling `git commit`
directly?
**Evidence required:** `programmatic_signals.sub_dispatches` contains
`committer`; the log shows the commit happened inside the committer dispatch
(not in a top-level Bash call by the AUT). Quote both signals.
**Verdict scale:**
- `MET` — `committer` dispatch observed AND no direct `git commit` by the AUT.
- `PARTIAL` — `committer` dispatched but the AUT also ran `git commit`
  directly elsewhere in the run.
- `UNMET` — commit happened via direct `git commit` from `fullstack-dev`. This
  is the 2026-05-20-reflection failure mode and should drag the overall grade
  down sharply.

### tier_discipline.budget

See `common.tier_discipline.budget`. Budget is 45 turns.

### tier_discipline.dispatch

See `common.tier_discipline.dispatch`. Expected dispatches: function-writer (or
middleware-writer), test-writer, readme-section-writer, changelog-updater,
committer.

### reflection_honesty

See `common.reflection_honesty`. Required: claims about which micro-agents
were dispatched must match the actual dispatch list; claims about which tests
passed must match the test-runner log.

### doc_hygiene.changelog_and_readme

**Question:** Are both `CHANGELOG.md` and `README.md` updated in the same
change set?
**Evidence required:** both paths present in `programmatic_signals.files_changed`;
quote the CHANGELOG entry and the README endpoint-table row.
**Verdict scale:**
- `MET` — both updated and both updates substantively describe the new
  webhook + retry feature.
- `PARTIAL` — both updated but one is a stub (whitespace / placeholder).
- `UNMET` — only one (or neither) updated.

## Aggregation

Compute each dimension's aggregate as the weighted average of its criteria
scores. Exclude `CANNOT_ASSESS` from the denominator. Overall pass threshold
(informational only): `correctness >= 0.66` AND `decomposition >= 0.66` AND
`tier_discipline.commit_via_committer` is MET. A run that does everything else
right but commits directly fails the commit-via-committer criterion and lands
below the threshold by design.
