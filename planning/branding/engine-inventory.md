## PART A — "Voltron Engine" Component Inventory

The **engine** is the machinery that differentiates Voltron from generic agent orchestrators (LangGraph / CrewAI / AutoGen). Where those are *Python libraries you write an app against*, Voltron is an **MCP server that drives Claude Code itself** — agents are markdown templates, execution is real Docker containers running the real `claude` CLI, and the system **rewrites its own templates** from production feedback. The differentiating components:

### Notes (Part A)

- **The genuinely novel triad:** (6) self-improvement reflection loop, (11) self-grading eval harness, and (10) Alexandria cross-project memory together make Voltron a **self-modifying, self-evaluating** orchestrator. That combination — agents defined as versioned markdown, edited by an automated PR pipeline, and regression-graded by an in-repo judge — is what most separates it from LangGraph/CrewAI/AutoGen.
- **The execution substrate is the *real* Claude Code CLI in Docker**, not an in-process SDK call. Differentiation lives as much in harness engineering (nested DooD, socket sudo-shim, cache-staggered fan-out, auth-mount minimization) as in agent design.
- **MCP-as-delivery:** the engine augments an existing agent rather than being a standalone runtime; "install" means scaffolding versioned templates into the user's repo with an auto-update channel.
- **Doc drift to fix during the branding pass:** `README.md:162` advertises `start_agent_in_docker`, but no such tool is registered in `src/index.js` (only `run_agent_in_docker` and `run_agent_in_docker_batch` exist). Flag for the docs upgrade.

## PART B — Code-Structure / Coupling Baseline

Facts to inform "should we reorganize to separate the engine?" — **no recommendation made here.**

### B1. Where each concern lives today (LOC)

| Layer | Primary files | Approx size | Nature |
|-------|---------------|-------------|--------|
| **Engine logic** (MCP server, Docker dispatch, reflection/journal/progress/analysis fs ops, install/repair) | `src/index.js` | **2,429 LOC** | Pure JS logic; defines all 18 tools + `dispatchOneAgent`. |
| **Agent-template content** (the 73 templates' prose) | `src/templates.js` | **~9,700 of 10,134 LOC** | Mostly markdown-in-JS string `content` fields. |
| **Infra constants** (Dockerfile, run-script, allow/deny, gitignore, type tags, helpers) | `src/templates.js` | **~430 LOC** (`:9873-10134`) | Engine-relevant config, **co-located with template prose**. |
| **Scripts** (auto-update hook, setup, apm manifest, one-off migration `.py`) | `scripts/` | `auto-update-agents.js` 12.9 KB, `setup.js` 9.7 KB, many historical `vNNN-*.py` | Consume `TEMPLATES` via import / re-derive content. |
| **Eval harness** | `voltron-evals/` | `runner.js` ~30 KB + `lib/`, `tasks/`, `rubrics/`, `schemas/`, `DESIGN.md` 110 KB | Self-contained subpackage; talks to engine over MCP. |
| **Docs** | `README.md` (30 KB), `docs/index.html` (53 KB), `docs/*.md` (15 design docs) | large | Pure documentation; no code dependency on engine internals. |

**Headline:** the codebase is effectively **two large files** — `src/index.js` (engine) and `src/templates.js` (content). They are already *physically* separated by concern (logic vs. prose), but joined by a single import surface.

### B2. How coupled are engine vs. content vs. docs?

- **Engine → content coupling is real but narrow, via one named import surface.** `src/index.js:16-29` imports from `./templates.js`: `TEMPLATES`, `AGENT_NAMES`, `ALL_NAMES`, `TEMPLATE_ALIASES`, `getTemplatesForType`, `VALID_PROJECT_TYPES`, `CLAUDE_MD_FOR_TYPE`, `DOCKERFILE_CONTENT`, `VOLTRON_RUN_SCRIPT`, `VOLTRON_ALLOW`, `VOLTRON_DENY`, `voltronGitignoreBlock`. The hot path `dispatchOneAgent` reads `TEMPLATES[agent_name]` for `.content`, `.category`, `.model`, `.nestable` (`src/index.js:1768-1790`). So the engine depends on the **shape** of template objects, not on any specific template's prose.
- **Content → engine coupling is essentially zero.** `src/templates.js` is data + small pure helpers (`getTemplatesForType`, `voltronGitignoreBlock`); it imports nothing from `index.js`. Templates reference the engine only *by describing tool names in prose* (e.g. "call `run_agent_in_docker`"), not by code.
- **Docs → engine coupling is zero at the code level** but **high at the content level** — `README.md` and `docs/index.html` hard-code tool tables, version badges, and behavior descriptions that must be hand-synced (CLAUDE.md "Documentation Rule" mandates same-commit updates). This is a maintenance coupling, not an import coupling. (See B1 drift: `start_agent_in_docker`.)
- **Infra constants are mis-filed.** `DOCKERFILE_CONTENT`, `VOLTRON_RUN_SCRIPT`, `VOLTRON_ALLOW/DENY`, `VOLTRON_GITIGNORE_ENTRIES`, `PROJECT_TYPE_TAGS`, `CLAUDE_MD_FOR_TYPE`, `getTemplatesForType` all live in `templates.js` (`:9873-10134`) but are **engine/infra config, not agent prose**. Anything separating "engine" from "content" must split this file, not just move it.

### B3. Shared state, fs paths, and what a separation would have to untangle

1. **The `TEMPLATES` object is the shared spine.** It is consumed by: `src/index.js` (dispatch + all template tools), `scripts/auto-update-agents.js`, `scripts/setup.js`, `scripts/build-apm-manifest.js`, and indirectly by `voltron-evals` (`lib/template-hash.js` hashes templates). Any module boundary must keep `TEMPLATES` importable by all of these, or introduce a published interface.
2. **Object-shape contract is implicit.** The engine reads `t.content/.category/.model/.nestable/.tags/.destination/.name/.description/.filename`. There is no schema/type guarding this contract — a separation would need to formalize it (TS interface or JSON schema) so engine and content packages don't drift.
3. **Two distinct filesystem-path regimes, both rooted in `index.js`:**
   - **Server-relative** (the repo itself): `reflections/` via `join(__dirname,"..","reflections")` in `submit_reflection` `:973` and `list_reflections` `:1177`. This path assumes the running server *is* the project-voltron repo — it's how the self-improvement loop writes back.
   - **Project-root-relative** (the user's repo): `.voltron/{journal,analyses,logs,tmp,progress.json,stringer}` resolved via `detectProjectRoot()` `:181-226`. Used by `append_journal`, `submit_analysis`, `update_progress`, and `dispatchOneAgent`.
   A separation must decide which package owns each regime — the reflection write-back path in particular blurs "engine" and "this-repo's content."
4. **The reflection self-improvement loop is inherently cross-cutting.** It spans `submit_reflection` (engine, `index.js`) → `reflections/*.json` (data) → `.github/workflows/process-reflections.yml` (CI) → harness-engineer template (content) → edits to `src/templates.js` (content) → `package.json` version bump (`CLAUDE.md` rule: version must reflect template state). This loop **deliberately couples engine + content + CI + versioning** and would be the hardest seam to cleanly split.
5. **Version coupling.** `VERSION` is read from `package.json` (`index.js:35-38`) and embedded into tool outputs and (via templates) into scaffolded agent files; `auto-update-agents.js` compares embedded vs. current version. Engine and content currently **share one version number** by design.

### B4. Existing seams that already look module-like

- **`voltron-evals/` is already a near-independent subpackage.** It has its own `runner.js`, `lib/`, `schemas/`, `README.md`, `DESIGN.md`, and—critically—**talks to the engine through the MCP protocol boundary** (`StdioClientTransport` spawning `src/index.js`), not via internal imports. It only reaches into source for `lib/template-hash.js`. This is the cleanest existing seam.
- **`dispatchOneAgent()` is already extracted** as a shared helper (`index.js:1758-2130`) used by both the singleton and batch tools — a de facto "dispatch core" already factored out of the tool handlers.
- **`scripts/` already consumes templates as a library**, proving `templates.js` works as an importable data module independent of the server (`setup.js`, `auto-update-agents.js`, `build-apm-manifest.js`).
- **Infra constants form a latent third module.** `DOCKERFILE_CONTENT` / `VOLTRON_RUN_SCRIPT` / `VOLTRON_ALLOW` / `VOLTRON_DENY` / `voltronGitignoreBlock` are cohesive "scaffold infra" already grouped at the tail of `templates.js` (`:9907-10107`) and could be lifted wholesale.
- **The MCP tool boundary itself is a seam.** Every capability is already exposed as a discrete `server.tool(...)` registration; the engine's public surface is already enumerated and protocol-mediated.
- **`detectProjectRoot()`** (`:181-226`) is a self-contained, dependency-free utility — a natural shared-util candidate.

### B5. Summary of facts (no recommendation)

- The repo is **logic (`index.js`) vs. data (`templates.js`)** already, but `templates.js` mixes agent prose with engine/infra config.
- Coupling is **one-directional and narrow**: engine imports a named set from content; content imports nothing back. The binding is the implicit `TEMPLATES` object-shape contract.
- The **reflection loop + shared version + dual fs-path regimes** are the cross-cutting threads any separation would have to untangle.
- **`voltron-evals/` (MCP-mediated), `scripts/` (template-as-library), `dispatchOneAgent` (extracted core), and the tail-of-`templates.js` infra block** are existing seams that already resemble module boundaries.
