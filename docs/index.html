V for all and All for one

Many agents. One engine. An orchestration engine that drives Claude Code and rewrites its own playbook.

One coordinator. Fifty-one specialists. Real containers.

Get started View on GitHub

Project Voltron is an orchestration engine that drives Claude Code with a real three-tier agent team, with each specialist running in its own Docker container, and then grades and rewrites those agents from what it learns in the field.

Three Pillars

Compose, don't prompt

A real org chart, enforced in code.

A depth-bounded three-tier hierarchy (coordinator → sub-manager → micro-agent) capped at depth 3 by the runtime, not by convention. Sub-managers compose single-verb micro-agents; the "never DIY" rule is baked into every template. 73 templates, 73 jobs, zero improvised monoliths.

Real isolation, real parallelism

Every agent gets its own container running the real Claude CLI.

Throwaway Docker containers, the actual claude binary, the repo bind-mounted, OAuth credentials read-only. Not an in-process SDK call. Fan out eight agents in one batch call, with a head-start gate that shares one prompt-cache write across the fleet. Tuned to Anthropic prompt-cache economics at the dispatch layer.

It improves itself

Voltron rewrites its own agents and grades them before they ship.

After each production session, agents submit structured reflections. A CI job runs the harness-engineer agent, which edits src/templates.js, bumps the version, and opens a PR. Before any updated agent ships, the voltron-evals harness regrades it through the same live dispatch path it uses in production. No other orchestrator self-modifies through a reviewed, regression-graded pipeline.

See it for real

voltron-glimpse: the dispatch graph, alive

The topology above is the map. voltron-glimpse is the territory: a real-time, read-only visualizer you run at the root of any Voltron project. A browser opens to a live animated graph of the agents whose Docker containers are running right now, plus the dispatch connections inferred between them. No setup, no writes, no history. Just a window onto what the engine is doing this second.

One node per live container

Every running voltron-* container becomes a node. Nodes pulse vivid green while working, then flash green for a clean exit or red for an error before fading out. The graph empties as the fleet finishes.

Size encodes tier

Node size maps to the same tier model as the rest of this page: Tier 1 orchestrators are largest, Tier 3 micro-agents smallest. The shape of a dispatch wave is legible at a glance.

Inferred dispatch edges

Dashed edges run from a synthetic scrum-master hub with a marching-ants animation, reconstructed from container timing. Hover or click any node for a detail card: agent name, container, dispatch time, the current [STEP N] or [DONE] from the log tail, and exit code.

Run it with no install at the root of a project that is dispatching agents:

npx github:7ports/voltron-glimpse  # opens http://127.0.0.1:7424

Prefer it on your PATH? npm install -g github:7ports/voltron-glimpse, then run voltron-glimpse at any project root. Node 20+ and Docker are required for the primary live mode.

Honest about what it is.

voltron-glimpse is strictly read-only: it never touches .voltron/ or .beads/. It is present-tense only, showing what is live now rather than replaying history. Dispatch edges are inferred from container timing, not declared by the agents. And it binds to localhost with no auth and no remote exposure, so it stays a tool for the trusted machine where your agents already run.

Quickstart

Three commands from zero to a full agent team

Prerequisites: Docker installed and running (specialists execute in containers), and beads for dependency-aware task tracking. You run Claude Code normally on your desktop, and Docker is handled behind the scenes.

1

Setup

Clone and run the one-command setup:

git clone https://github.com/7ports/project-voltron.git
cd project-voltron
node scripts/setup.js

Installs dependencies, registers the MCP server, and configures the global allowlist. Restart Claude Code when prompted.

2

Scaffold

In any project, ask Claude Code:

"Scaffold this web project
 with Voltron agents"

"Scaffold this Unity project
 with Voltron agents"

Agent files are written straight to .claude/agents/, with no manual copy-paste. Smart merge preserves your existing files.

3

Develop

Fill in CLAUDE.md, then invoke agents:

/scrum-master         # plan
@agent-fullstack-dev  # React + Node
@agent-csharp-dev     # Unity C#
@agent-devops-engineer

/scrum-master is a slash command that runs in your main session so it can stream agent output live.

How you use it

Scaffold → plan → dispatch → reflect

From backlog to shipped code, with agents coordinated at every step.

  1. Scaffold Run scaffold_project to write CLAUDE.md, agent files, Dockerfile.voltron, the launch script, and the auto-update hook for your project type. Smart merge skips existing files and appends to existing CLAUDE.md.
  2. Plan Invoke /scrum-master in your main session with a project plan. It decomposes the work into agent-sized tasks with dependencies and acceptance criteria, tracked as a real DAG in beads, and never implements anything itself.
  3. Dispatch The scrum-master calls run_agent_in_docker (or run_agent_in_docker_batch for parallel waves). Each agent runs autonomously inside Docker with --dangerously-skip-permissions; file changes are visible on the host via the volume mount.
  4. Reflect At phase completion, blockers, and session end, the scrum-master submits structured reflections. Tool-specific discoveries sync to Alexandria so the next project starts ahead.

The differentiator

The Voltron Engine

The machinery beneath the templates, and the reason Project Voltron is more than a bundle of markdown files. A self-modifying, self-evaluating orchestration engine: agents are versioned markdown, execution is real Docker containers running the real claude CLI, and the system rewrites and regrades its own agent definitions from production feedback. The templates are what the engine produces; the engine is what you adopt.

Three-tier hierarchy

A real org chart in code: coordinator decomposes, sub-managers own domains, micro-agents do one focused edit each. Depth-capped at 3 by the runtime; 73 templates.

Docker-isolated execution

Each agent runs in a throwaway container with the actual claude CLI, not an in-process SDK call. Full transcript captured; auth minimal by design.

Parallel batch dispatch

Fan out 2 to 8 agents in one MCP call, with a head-start gate that shares one prompt-cache write across the whole fleet.

Nested Docker-out-of-Docker

Tier-2 agents inside containers can spawn Tier-3 siblings via the mounted host socket. Real containers all the way down.

Dependency-graph tracking

Work is a real DAG on a versioned Dolt database (beads), not a TODO list. Dependency-aware planning is a first-class substrate.

Post-session reflection loop

Agents submit structured feedback; CI runs the harness-engineer to edit templates, bump the version, and open a PR. The product rewrites itself from field data.

MCP-as-delivery channel

The engine ships as an MCP server that augments Claude Code directly. Install means scaffolding versioned templates into your repo with an auto-update channel.

voltron-evals regression harness

Agents are graded through the live MCP dispatch path they run in production, scored by deterministic signals plus a Sonnet judge. Voltron ships a graded regression suite for its own prompts.

Alexandria cross-project memory

Tool and setup knowledge flows out of every session into a shared, searchable guide store: a second self-improving substrate alongside the reflection loop.

Self-improvement

It rewrites its own agents and grades them first

The novel triad: a reflection loop feeds an automated PR pipeline, an in-repo judge regression-grades every change before it ships, and a cross-project memory accrues operational knowledge. No other orchestrator self-modifies through a reviewed pipeline.

  1. Sessions submit reflectionsProduction agents drop structured JSON feedback into reflections/, tied to project type and the agents used.
  2. CI runs the harness-engineerA scheduled GitHub Actions job groups feedback by agent, prioritizes by frequency, edits src/templates.js, bumps the version, and opens a PR.
  3. voltron-evals regrades before mergeThe harness dispatches the updated agent through the same live MCP path it uses in production, scored by deterministic signals plus a self-preference-controlled Sonnet judge.
  4. Human reviews, merges, shipsA reviewer approves the diff. On merge, the UserPromptSubmit auto-update hook silently refreshes installed agent files at the next session start.

Architecture & internals

Depth, with honesty

The tier model, Docker isolation, nested dispatch, the beads DAG, and the cost/cache optimizations, plus the trust boundary they depend on.

  • Tier model & depth capSub-managers (Tier 2) may dispatch micro-agents (Tier 3) but micro-agents cannot dispatch further. The depth-cap guard in run_agent_in_docker refuses any 4th-tier launch, and every Tier-3 template is tagged nestable: false.
  • Nested Docker-out-of-DockerThe MCP server resolves host paths via VOLTRON_HOST_ROOT / VOLTRON_HOST_HOME / VOLTRON_HOST_TMPDIR so the inner docker run sees the real host filesystem, mounts the Docker socket, and generates a container-mcp.json so the nested Claude Code has its own project-voltron MCP.
  • Cost & cache-aware dispatchA cacheable system-prompt prefix, de-duplicated CLAUDE.md / bd-prime context, staggered batch fan-out, and a bounded ~4 KB result tail. Tuned to Anthropic prompt-cache economics at the harness layer.
  • Dependency-aware planningTasks are a real DAG on a versioned Dolt database via beads, so what blocks what is first-class, not a flat TODO list.
Security disclosure: trusted machines only.

To make nested dispatch work, /var/run/docker.sock is mounted into every agent container. Inside a container, having that socket is equivalent to root on the host: an agent can launch privileged containers, mount any host path, and read or write anything the Docker daemon can. Only run Voltron on a trusted developer machine, and only with prompts you trust. Do not point it at untrusted user input, public webhooks, or shared CI without a hardened sandbox in front.
